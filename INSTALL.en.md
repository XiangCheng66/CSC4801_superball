# Installation Guide

[中文](INSTALL.md) | **English**

Accounts, profiles/private resumes/job recommendations, applications and own application lists, company/job management and employer interview slots are available. Employer applicant/status management and candidate booking creation are integrated. The unified `seed_demo` command resets business data and provides the complete demo dataset.

## Prerequisites and Versions

- Native development: Python 3.11 or 3.12, Node.js 22 (at least 22.12, below 23), npm 10/11, PostgreSQL 17.
- Containers: Docker Engine/Desktop and Compose supporting `docker compose up --wait`. Images are explicitly declared in Dockerfile/compose.yaml: `node:22-bookworm-slim`, `python:3.12-slim-bookworm`, `postgres:17-bookworm`. Container-only use does not require Node, Python or PostgreSQL on the host.
- Complete Python dependency versions are pinned in `requirements.lock`; direct dependency ranges are in `requirements.in`. React/build/test dependencies are locked in `frontend/package-lock.json`.
- Core functionality, unit tests and browser tests do not use third-party models or paid APIs.

## Environment Variables

Copy the configuration at the repository root (Windows PowerShell):

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

On macOS/Linux, use `test -f .env || cp .env.example .env`. Replace the `DJANGO_SECRET_KEY` and `POSTGRES_PASSWORD` placeholders in `.env` with random values generated by a password manager, or an existing Python installation using `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Do not commit `.env`; both manage.py and Compose read it.

| Variable | Purpose / local value |
|---|---|
| `DJANGO_DEBUG` | Example default: `0`; use `1` only for local development/debugging |
| `DJANGO_SECRET_KEY` | Stable local secret; when DEBUG=0, must contain at least 50 characters and must not be an example placeholder |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1`, comma-separated |
| `DATABASE_ENGINE` | Defaults to `postgresql`; `sqlite` is an explicit lightweight development option only |
| `POSTGRES_DB` / `POSTGRES_USER` | Both default to `superball` |
| `POSTGRES_PASSWORD` | Local database password, matching the password used to create the database |
| `POSTGRES_HOST` / `POSTGRES_PORT` | Native default: `127.0.0.1:5432`; `POSTGRES_PORT` also controls the Compose host mapping, while the app container still connects to `db:5432` |
| `APP_PORT` | Compose host web port, default `8000`; change it to avoid conflicts with native Vite or other instances |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Defaults to local Vite origins: `http://localhost:5173,http://127.0.0.1:5173` |
| `DJANGO_SECURE_COOKIES` | `0` for local HTTP; use `1` for HTTPS |
| `SEED_AUTH_DEMO` | Default `0`; when set to `1` locally, startup only adds missing accounts from the four authentication demo accounts and preserves existing accounts/passwords |
| `TEST_DATABASE_ENGINE` | Defaults to an isolated in-memory SQLite test database; `postgresql` uses a separate `test_<POSTGRES_DB>` database |

## Docker Build and Startup

Start from a clean checkout of the target commit. Prepare `.env` at the repository root, then run:

```bash
docker compose pull db
docker compose build app
docker compose up -d --no-build --wait --wait-timeout 120
docker compose exec -T app python manage.py seed_demo
docker compose ps
```

Open **http://127.0.0.1:8000** (or the configured `APP_PORT`). The image build runs frontend unit tests and bundles React. Once PostgreSQL's TCP port is ready, the app automatically runs migrations and starts Gunicorn. `--wait` confirms both services are healthy before seeding. `/api/health/` should return `data.status=ok` and `data.database=postgresql`.

For acceptance testing or parallel development, use a separate checkout with different `APP_PORT` and `POSTGRES_PORT` values, and the same distinct project name on every Compose command, such as `docker compose -p superball-review …`, to isolate database volumes from existing environments.

The standalone application build command is `docker build -t superball-app .`. Use the Compose sequence above for the complete database/application environment; dependency images are pulled explicitly.

Common commands:

```bash
docker compose logs app
docker compose exec app python manage.py migrate --noinput
docker compose exec -T app python manage.py seed_demo
docker compose exec -T app python -m pytest tests/unit -q -o cache_dir=/tmp/pytest-cache
docker compose exec -T -e TEST_DATABASE_ENGINE=postgresql app python -m pytest tests/unit -q -o cache_dir=/tmp/pytest-cache
docker compose down
```

The `postgres_data` volume survives ordinary `down`. To completely reset this local Compose demo database, run `docker compose down --volumes`, then repeat startup and seeding. This deletes the database volume for this Compose project.

See [A final handoff](docs/A_FINAL_HANDOFF.md) for build/container acceptance evidence. Tests above store their cache in /tmp for the image's non-root student user. PostgreSQL test databases are only for tests; unit tests do not require seeding.

## Local Development

### 1. Database

Install PostgreSQL 17 ([official Windows downloads](https://www.postgresql.org/download/windows/)). Connect to `psql` as a local administrator and run once, using the same password as `.env`:

```sql
CREATE ROLE superball LOGIN PASSWORD 'replace-with-a-local-database-password' CREATEDB;
CREATE DATABASE superball OWNER superball;
```

`CREATEDB` supports isolated local PostgreSQL test databases. Alternatively, run only the database with `docker compose up -d db`. For an existing local database, configure its user, database and port to avoid conflicts.

### 2. Backend (Terminal 1, Repository Root)

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate --noinput
.\.venv\Scripts\python.exe manage.py seed_demo
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

macOS/Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py seed_demo
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

`GET http://127.0.0.1:8000/api/health/` should return `data.status=ok` and `data.database=postgresql`. It performs a real query; initializing tables still requires the migration command above.

### 3. Frontend (Terminal 2)

```bash
cd frontend
npm ci
npm run dev
```

Use `npm.cmd` if PowerShell execution policy blocks npm.ps1. Open **http://127.0.0.1:5173**. Vite proxies `/api/` to `127.0.0.1:8000`, preserving same-origin browser cookies and CSRF.

If the backend port changes, set `API_PROXY_TARGET` before starting Vite. If the frontend port changes, also update `DJANGO_CSRF_TRUSTED_ORIGINS` and restart the backend. `npm run build` produces `frontend/dist`; Dockerfile copies it to `/app/frontend_dist`.

## Running Unit Tests

Backend (repository root; no development server required):

```powershell
.\.venv\Scripts\python.exe -m pytest tests/unit -q
```

Tests default to an isolated in-memory SQLite database. To verify PostgreSQL, ensure the database configured in `.env` is available, then run:

```powershell
$env:TEST_DATABASE_ENGINE = 'postgresql'
.\.venv\Scripts\python.exe -m pytest tests/unit -q
Remove-Item Env:TEST_DATABASE_ENGINE
```

On macOS/Linux: `TEST_DATABASE_ENGINE=postgresql .venv/bin/python -m pytest tests/unit -q`. pytest-django creates/cleans only `test_<POSTGRES_DB>`; unit tests do not use the application's demo database.

Frontend (in frontend):

```bash
npm test
npm run build
```

Run only C's matching tests (macOS/Linux, repository root):

```bash
.venv/bin/python -m pytest tests/unit/test_matching.py -v
```

Real cases cover profiles/recommendations, applications/own application lists, company/job and slot management. SQLite skips only two concurrency tests requiring PostgreSQL row locks; PostgreSQL runs the full suite.

Run `migrate`, then `python manage.py seed_demo` to reset and populate all demo data in one command. The full browser suite depends on this dataset. Start the services, then run in frontend:


## Troubleshooting

- Database connection failure: confirm PostgreSQL is running and `.env` host, port and password match the database. Native and Compose container port settings differ.
- Missing relation/table: run `manage.py migrate --noinput` first. Do not commit personal database files or modify shared initial migrations.
- Login/registration returns 403 `csrf_failed`: use the same site hostname throughout; do not mix localhost and 127.0.0.1. Use shared request helpers and check Cookie/Origin configuration.
- 401: not logged in or session expired. Log in again; changing SECRET_KEY invalidates old sessions.
- Incompatible Node engine: use Node 22.12+ within the 22 series. If npm 10 reports an internal `edgesOut` error during installation, run `npx --yes npm@11 ci` without changing the global installation.
- Backend `/` returns `frontend_not_built`: use Vite on port 5173 during native development. Container builds copy and serve frontend files.
- Port occupied: change `.env` `APP_PORT` / `POSTGRES_PORT` for Docker; adjust proxy target or CSRF configuration for Vite development.
- `up --wait` fails: inspect startup errors with `docker compose ps` and `docker compose logs db app`. Changing `.env` does not automatically change passwords inside an initialized database volume.
